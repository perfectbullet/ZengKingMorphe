# 四、Step 8 的 141 个非法实体类型不是 LLM 乱抽造成的

这是本轮最重要的技术问题。

## Step 6 使用的 extraction profile

允许实体类型：

```text
Technique
Tool
Material
Object
VisualEffect
Process
Parameter
Concept
```

## Step 8 使用的通用 schema

允许实体类型：

```text
CONCEPT
DEFECT
EQUIPMENT
MATERIAL
METHOD
PROCESS
PRODUCT
PROPERTY
SAFETY_REQUIREMENT
TOOL
```

两者明显不一致。

当前教材的实体分布是：

```text
material       93
visualeffect   89
technique      48
tool           27
concept         7
process         5
object          4
```

Step 8 报告的非法实体数：

```text
141
```

刚好等于：

```text
visualeffect 89
+ technique 48
+ object 4
= 141
```

因此这 141 个并不是 extraction profile 违反规则，而是：

> Step 6 按教材专属 profile 正确抽取，Step 8 却使用另一套通用工业 schema 进行审计。

这会让质量分出现系统性误判。

## 正确做法

Step 8 必须使用和 Step 6 相同的 profile，至少应接受：

```text
Technique
Tool
Material
Object
VisualEffect
Process
Parameter
Concept
```

不应再用当前这份通用 `industrial_training_kg_schema.v1.json` 直接判定。

# 六、Step 6 抽取过滤仍然确实存在问题

虽然 Step 8 的 schema 审计有误判，但 Step 6 的导入报告仍暴露了真实问题。

## 实体接受率

```text
raw_entity_mentions:      1278
accepted_entity_mentions: 496
rejected_entity_mentions: 782
接受率:                    38.81%
```

被拒绝样本包括：

```text
珠宝首饰 → product
设计师   → role
工艺师   → role
```

其中：

* `设计师、工艺师`可以按当前范围直接拒绝，因为 profile 明确不强调人物或角色；
* `珠宝首饰 → product`则是有效核心实体，不应直接丢失。

可以归一化为：

```text
product → Object
```

或者让模型严格输出 `Object`。

## 关系接受率

```text
raw_relation_mentions:      1066
accepted_relation_mentions:   64
rejected_relation_mentions: 1002
接受率:                       6.00%
```

其中：

```text
invalid_relation_endpoint: 851
invalid_relation_keyword:  151
```

`invalid_relation_endpoint` 大部分是级联错误：

```text
珠宝首饰被按 product 拒绝
        ↓
所有以“珠宝首饰”为端点的关系继续被拒绝
```

例如：

```text
珠宝首饰 → 宝玉石
珠宝首饰 → 贵金属
珠宝首饰 → 设计
```

因此修复顺序应当是：

```text
先修实体类型归一化
→ 再重新统计关系端点失败
→ 最后处理关系关键词
```

不能先盲目扩充关系关键词。
