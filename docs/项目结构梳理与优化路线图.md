### 2.3 ⭐ 关键约束：API 接口稳定性（共享前端）

两个分支 = 两个产品，但**前端只有一套**。这意味着：

```
前端（不变）
  │
  ├── POST /api/chat/v1/chat/completions  ← 请求/响应格式必须一致
  ├── POST /api/chat/v2/chat/completions  ← 请求/响应格式必须一致
  ├── /health                              ← 返回格式不变
  │
  └── ai-service（两个分支，部署时二选一）
        ├── math-before-industrial → :8100（数学产品）
        └── backup/industrial-training-before-unified-refactor → :8100（工业产品）
```

**不可修改的契约**：

1. `/api/chat/v1/chat/completions` 和 `/api/chat/v2/chat/completions` 的请求体 JSON Schema
2. 流式响应的 chunk 格式（`data: {...}\n\n`）
3. 错误响应的 JSON 格式
4. `/health` endpoint 的返回

**可以不同的**：

- `user_query` 内部走哪个 LangGraph 节点分支
- RAG 检索的数据源和召回逻辑
- LLM 模型的地址（通过 env 切换）
- 系统提示词和后处理策略

### 2.4 分支管理策略

| 问题 | 结论 |
|---|---|
| 为什么两个分支不合并？ | 两个产品的 LangGraph workflow、RAG 数据源、ASR 后处理完全不同，合并会导致大量 `if product == "math"` 分支，可维护性下降 |
| 公共 bugfix 怎么传？ | 单向 cherry-pick：先在 `math-before-industrial` 修复 → 如 `backup/` 也有相同代码则回贴；如不同则各自修 |
| 什么时候考虑合并？ | 当 `backup/industrial-training-before-unified-refactor` 被正式激活、且发现共享代码 > 80% 时再评估 |
| 分支命名建议 | 当前 `backup/industrial-training-before-unified-refactor` 太冗长，建议短名为 `feature/industrial-product`（若激活）或保持现状（若暂停） |

### 4.2 命名规范建议

当前命名无系统前缀，建议按域划分：

```
INFRA_       基础设施（数据库、缓存）
MODEL_       LLM / Embedding / Reranker 模型配置
```

**命名规则**：`<DOMAIN>_<RESOURCE>_<PROPERTY>`，全部大写 + 下划线。

### 4.3 分文件加载方案

将 `.env` 拆分为**四层文件**，按顺序叠加加载（后加载的覆盖前加载）：

```
ai-service/
├── .env.infra.example       # 基础设施模板（MongoDB/ES/Milvus/Neo4j）
├── .env.models.example      # 模型端点模板（LLM/Embedding/Reranker）
├── .env.rag.example         # RAG 链路模板（LightRAG 参数）
├── .env.app.example         # 应用层模板（端口/日志/开关/安全）
├── .env.infra               # ★ 本地实际值（不提交）
├── .env.models              # ★ 本地实际值（不提交）  ← 切换模型端点只改这里
├── .env.rag                 # ★ 本地实际值（不提交）
└── .env.app                 # ★ 本地实际值（不提交）
```

**使用方式（核心）**：当需要切换模型端点时，只改 `.env.models` 里的 `MODEL_*_BASE_URL`，指向 `docs/model-endpoint-registry.md` 中对应的服务器 IP 即可。

**加载机制**（`config.py` 中实现）：

```python
from dotenv import load_dotenv
for f in [".env.infra", ".env.models", ".env.rag", ".env.app"]:
    load_dotenv(os.path.join(os.path.dirname(__file__), f), override=False)
```

### 5.2 为什么两个产品不交替部署

**不是硬冲突，而是设计如此**：

- 两个产品有不同的 RAG 数据源、不同的 LangGraph workflow、不同的 ASR 后处理
- 但它们**共享同一套前端**，前端不感知后端是哪个产品
- 部署时二选一：要么启 math 产品（8100），要么启工业产品（8100），前端连同一个端口
- 两个 ai-service 实例不能同时占 8100 → 这是设计约束，不是技术 bug

### 5.3 切换产品的操作流程

```bash
# 从数学产品切到工业产品（服务器上）
cd /data/metahuman_work/ZengKingMorphe-math
./start_ai_service.sh stop
```

## 附录

### A. ai-service 内部路由（LangGraph workflow）

```
用户请求
  → intent_classifier
  → finalize_classification（启发式补位：数学关键词 / 工业关键词 / ASR 检测）
  → noise_gate（无意义词拦截）
  → answer_mode_router
      ├── MATH_LLM → 数学模型直连 → 后处理
      ├── RAG_WITH_FALLBACK → LightRAG 检索 → RAG 增强回复
      ├── WEB_SEARCH → Tavily 联网 → 实时信息回复
      ├── GENERAL_LLM → 通用 LLM 直接回复
      └── PRESET_RESPONSE → 预设话术
```

### B. 环境变量域分组（目标态）

```
[INFRA_]      基础设施（MongoDB / ES / Milvus / Neo4j 连接信息）
[MODEL_]      模型端点（LLM / Embedding / Reranker 的 BASE_URL 和 NAME）
[RAG_]        RAG 参数（LightRAG working_dir / 检索阈值 / top_k 等）
[WEB_]        联网搜索（Tavily API key / timeout / depth）
[APP_]        应用自身（port / workers / log_level / max_context_turns）
[SECURITY_]   认证（API key / JWT secret）
[DEBUG_]      调试开关（graph dump / rag stream debug）
```
