#### 1.6 联网检索功能

**需求说明**：当用户问题需要实时信息（如天气、新闻）或知识库中没有相关内容时，系统应能够通过联网查询获取相关资料后回复用户。

**参考实现**：基于`docs/langgraph_crag.ipynb`中的CRAG（Corrective RAG）模式

**核心流程**：

```
用户查询
    ↓
知识库检索（RAG）
    ↓
文档相关性评分
    ↓
┌──────────┴──────────┐
│ 相关性判断           │
└──┬──────────┬───────┘
   │          │
高相关性   低相关性/无结果
   │          │
   │      联网检索
   │          │
   └────┬─────┘
        ↓
    答案生成
```

**实现要求**：

1. **文档相关性评分**（参考langgraph_crag.ipynb）：
   - 对检索到的文档进行相关性打分（0-1分）
   - 设置相关性阈值（建议：0.6）
   - 分数高于阈值：使用知识库文档
   - 分数低于阈值或无结果：触发联网检索

2. **联网检索触发条件**：
   - 知识库检索无结果
   - 知识库文档相关性得分 < 0.6
   - 用户问题包含实时性关键词：
     - 时间类：今天、明天、最近、现在
     - 天气类：天气、气温、降雨
     - 新闻类：新闻、热点、最新
     - 市场类：股价、汇率、行情

3. **联网检索实现**：
   - 使用搜索引擎API（如Tavily、SerpAPI、Bing Search API）
   - 提取搜索结果摘要（Top 3-5条）
   - 对搜索结果进行相关性过滤
   - 结合搜索结果生成答案

4. **答案生成策略**：
   - **仅知识库**：相关性高，直接使用知识库
   - **仅联网**：知识库无结果，使用搜索结果
   - **混合模式**：知识库+联网搜索结果结合

5. **LangGraph工作流集成**：

```python
# 新增节点
graph.add_node("grade_documents", grade_documents)  # 文档打分
graph.add_node("web_search", web_search)            # 联网检索

# 条件边：根据文档相关性决定是否联网
graph.add_conditional_edges(
    "grade_documents",
    lambda state: "web_search" if state["relevance_score"] < 0.6 else "generate_answer",
    {
        "web_search": "web_search",
        "generate_answer": "generate_answer"
    }
)

graph.add_edge("web_search", "generate_answer")
```

6. **文档打分实现**（参考langgraph_crag.ipynb）：

```python
async def grade_documents(state: ConversationState) -> ConversationState:
    """对检索文档进行相关性打分"""
    query = state["user_query"]
    docs = state["retrieved_docs"]
    
    if not docs:
        state["relevance_score"] = 0.0
        return state
    
    # 使用LLM对文档相关性打分
    grading_prompt = f"""
    用户问题：{query}
    
    检索文档：{docs[0]['content'][:500]}
    
    请评估该文档与用户问题的相关性，返回0-1之间的分数。
    - 1.0: 高度相关，能直接回答问题
    - 0.6-0.9: 相关，包含部分有用信息
    - 0.3-0.5: 弱相关，信息不够充分
    - 0.0-0.2: 不相关
    
    仅返回数字分数，如：0.85
    """
    
    score = await llm.complete(grading_prompt, temperature=0.1)
    state["relevance_score"] = float(score.strip())
    
    return state

async def web_search(state: ConversationState) -> ConversationState:
    """联网检索"""
    from tavily import TavilyClient
    
    client = TavilyClient(api_key=settings.TAVILY_API_KEY)
    
    # 执行搜索
    search_results = client.search(
        query=state["user_query"],
        max_results=5
    )
    
    # 提取搜索结果
    web_docs = [
        {
            "content": result["content"],
            "url": result["url"],
            "title": result["title"]
        }
        for result in search_results["results"]
    ]
    
    state["web_search_results"] = web_docs
    state["retrieved_docs"].extend(web_docs)  # 合并到检索文档中
    
    return state
```

7. **配置要求**：
   - 搜索引擎API Key配置
   - 相关性阈值可配置
   - 联网检索超时时间配置（建议5秒）
   - 搜索结果数量配置（建议3-5条）

**注意事项**：
- 联网检索会增加响应时间，需在超时时降级
- 搜索结果需要标注来源URL，增强可信度
- 敏感话题（政治、宗教等）应禁用联网检索
- 联网检索调用需计入成本控制

  ```
  文档上传 → 格式验证 → 文本提取 → 预处理 → 分块 → 向量化 → 存储
  ```

- **异步处理**：
  - 任务队列（Celery/RQ）
  - 处理进度查询
  - 失败重试机制
  - 处理日志记录

- **质量检查**：
  - 文本提取质量评估
  - 分块质量检查
  - 向量化成功率
  - 异常文档标记

- **管线配置**：
  - 可视化配置界面
  - 预设处理模板
  - 自定义处理步骤
  - 管线性能监控

#### 2.5 混合检索策略

**补充需求**：

- **多路检索**：
  - **向量检索**（Chroma）：语义相似度匹配
  - **关键词检索**（ElasticSearch）：精确关键词匹配
  - **全文检索**（ElasticSearch）：BM25算法
  - **专业词库增强**：实体识别、同义词扩展

- **检索融合算法**：
  - **RRF（Reciprocal Rank Fusion）**：
    ```python
    score(d) = Σ 1 / (k + rank_i(d))
    ```
  - **加权融合**：
    ```python
    score(d) = w1 * vector_score + w2 * keyword_score
    ```
  - **CombSUM/CombMNZ**：传统融合算法

- **检索优化**：
  - 查询扩展（Query Expansion）
  - 查询重写（Query Rewriting）
  - 同义词替换
  - 拼写纠错
  - 停用词过滤

- **重排序（Rerank）**：
  - 使用专用重排序模型（bge-reranker）
  - 基于上下文的重排序
  - 基于用户偏好的重排序
  - 多样性保证（避免重复结果）

### 4. 词库管理

**需求说明**：专业词库和敏感词库均由Java平台端提供接口管理，AI侧仅负责调用接口获取数据并应用到检索增强和内容过滤中。

#### 4.1 专业词库

**用途**：
- 查询扩展：使用同义词增强检索效果
- 实体识别：识别行业专业术语、产品名称、人名地名等
- 检索增强：提高专业领域问题的召回率

**Java端接口**（已在1.5.2节定义）：
- `GET /api/java/professional-words/list` - 查询专业词列表
- `POST /api/ai/professional-words/sync-notify` - 专业词变更通知

**AI侧应用场景**：
1. **查询预处理**：识别用户问题中的专业术语，扩展同义词
2. **检索增强**：对专业术语进行精确匹配或语义匹配
3. **实体提取**：从对话中提取关键实体信息
4. **上下文理解**：根据专业词库理解领域特定表达

#### 4.2 敏感词库

**用途**：
- 用户输入过滤：拦截敏感问题和违规内容
- AI输出过滤：确保生成内容的安全性和合规性
- 内容审核：对对话内容进行安全审核

**Java端接口**（已在1.5.1节定义）：
- `GET /api/java/sensitive-words/list` - 查询敏感词列表
- `POST /api/ai/sensitive-words/sync-notify` - 敏感词变更通知

**AI侧应用场景**：
1. **输入拦截**：在对话引擎处理前检测敏感内容
2. **输出过滤**：在AI生成答案后检测敏感内容
3. **日志记录**：记录敏感词触发情况，供审计使用
4. **分级处理**：根据敏感级别（critical/warning/notice）采取不同策略

#### 4.3 词库同步机制

**需求**：
- **启动时全量同步**：AI服务启动时从Java端同步全量词库数据
- **增量更新**：监听Java端Webhook，实时接收词库变更通知
- **定时同步**：定期（如每小时）从Java端同步数据，确保一致性
- **本地缓存**：将词库数据缓存到内存或Redis，提高检索性能

**同步流程**：
```
AI服务启动
    ↓
全量同步专业词库和敏感词库
    ↓
构建内存索引（AC自动机/Trie树）
    ↓
监听Java端Webhook
    ↓
接收变更通知 → 增量更新索引
```

#### 4.4 词库应用优化

**需求**：
- **高性能匹配**：使用AC自动机或DFA算法实现敏感词快速匹配
- **同义词扩展**：支持专业词同义词的自动扩展
- **优先级匹配**：根据词库优先级决定匹配策略
- **缓存优化**：将热点词汇缓存到内存，减少检索开销

### 1. LangGraph工作流设计

**LangGraph在项目中的应用**：

```python
from langgraph.graph import StateGraph, END
from typing import TypedDict, Annotated
from operator import add

# 定义对话状态
class ConversationState(TypedDict):
    messages: Annotated[list, add]
    user_query: str
    user_id: str
    session_id: str
    employee_id: str  # 数字员工工号
    employee_config: dict  # 数字员工配置
    intent: str
    entities: dict
    retrieved_docs: list
    final_answer: str
    confidence: float
    context: dict

# 构建对话图
def build_conversation_graph():
    graph = StateGraph(ConversationState)
    
    # 添加节点（各个处理步骤）
    graph.add_node("input_validation", validate_input)
    graph.add_node("sensitive_check", check_sensitive_words)
    graph.add_node("intent_recognition", recognize_intent)
    graph.add_node("entity_extraction", extract_entities)
    graph.add_node("knowledge_routing", route_to_knowledge)
    graph.add_node("hybrid_retrieval", hybrid_search)
    graph.add_node("context_enhancement", enhance_with_context)
    graph.add_node("answer_generation", generate_answer)
    graph.add_node("quality_check", check_answer_quality)
    graph.add_node("output_filter", filter_output)
    graph.add_node("save_conversation", save_to_db)
    
    # 添加边（工作流程）
    graph.add_edge("input_validation", "sensitive_check")
    
    # 条件边：敏感词检测通过则继续，否则结束
    graph.add_conditional_edges(
        "sensitive_check",
        lambda state: "continue" if not state.get("has_sensitive") else "reject",
        {
            "continue": "intent_recognition",
            "reject": END
        }
    )
    
    graph.add_edge("intent_recognition", "entity_extraction")
    graph.add_edge("entity_extraction", "knowledge_routing")
    graph.add_edge("knowledge_routing", "hybrid_retrieval")
    graph.add_edge("hybrid_retrieval", "context_enhancement")
    graph.add_edge("context_enhancement", "answer_generation")
    graph.add_edge("answer_generation", "quality_check")
    
    # 条件边：质量检查通过则继续，否则降级处理
    graph.add_conditional_edges(
        "quality_check",
        lambda state: "pass" if state.get("confidence", 0) > 0.7 else "fallback",
        {
            "pass": "output_filter",
            "fallback": "answer_generation"  # 重新生成或返回默认回答
        }
    )
    
    graph.add_edge("output_filter", "save_conversation")
    graph.add_edge("save_conversation", END)
    
    # 设置入口
    graph.set_entry_point("input_validation")
    
    return graph.compile()
```

## 六、风险与挑战

### 1. 技术风险

- **LLM API稳定性**：
  - 风险：OpenAI API可能不稳定或限流
  - 应对：实现多模型备份方案，支持DeepSeek/Qwen

- **向量检索准确性**：
  - 风险：向量检索召回率不足
  - 应对：混合检索策略（向量+关键词）

- **性能瓶颈**：
  - 风险：高并发下性能不足
  - 应对：缓存优化、异步处理、水平扩展

### 2. 业务风险

- **知识库质量**：
  - 风险：知识库内容不准确或过时
  - 应对：建立知识库质量管理流程

- **用户满意度**：
  - 风险：回答质量不满足用户期望
  - 应对：持续优化Prompt、知识库和检索策略

### 3. 成本风险

- **LLM调用成本**：
  - 风险：高频调用导致成本过高
  - 应对：缓存机制、批处理、选用性价比高的模型
